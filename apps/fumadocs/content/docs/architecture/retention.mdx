---
title: Retention
description: How long messages, attachments and other records are kept, and how they are cleaned up.
---

<Status kind="decided" /> Messages are kept for **30 days** by default. Each topic can set its own `retentionDays` from 1 to 365 (`RETENTION_DAYS` in `packages/contract/src/topic.ts`).

## Rules

| Record | Kept until |
| --- | --- |
| Message | `expiresAt`, set at publish time from the topic's retention |
| Responses and read state | Deleted with their message |
| Attachment file | Deleted with its message |
| Uploaded attachment never used in a message | 1 hour after upload |
| Accepted, expired or revoked invite | 30 days after it ends |
| Device not seen | 60 days after `lastSeenAt` |
| Expired access token | Kept, so it still shows as expired in the token list |

Changing a topic's retention affects only new messages. Existing messages keep the `expiresAt` they were published with, so a mistaken setting never wipes history.

## Cleanup job

A Cron Trigger runs the cleanup every hour:

<Steps>
<Step>

### Find expired messages

Select a batch of up to 500 messages where `expires_at < now`, using the `expires_at` index.

</Step>
<Step>

### Delete files first

Delete their R2 objects. If deleting a file fails, its message stays and the next run tries again, so no row ever points to a missing file.

</Step>
<Step>

### Delete rows

Delete the messages; responses and read state cascade. Repeat until nothing is expired or the run's time budget is used up.

</Step>
<Step>

### Sweep the rest

Delete orphaned uploads, old invites and stale devices.

</Step>
</Steps>

The apps and the API never show a message past its `expiresAt`, even if cleanup has not run yet.
